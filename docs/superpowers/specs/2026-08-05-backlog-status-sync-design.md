# 설계: BACKLOG 상태 동기화 — 갱신 묶음 항목 + check-docs §7

## 문제 / 목표

파생 프로젝트(`mobius4-dev-tool`)에서 백로그 41건을 코드에 대고 전수조사한 결과 4건의 상태가
실제와 달랐고, 그중 하나는 **이 스캐폴드가 물려준 구조적 빈틈**이다. 구현·테스트·릴리즈까지
끝난 항목이 백로그 표에 `🔄 진행중`으로 남아 있었다.

원인은 `.claude/rules/readme-sync.md`의 "완료 시 자동 갱신 묶음" 2번이다.

```
2. .claude/workspace/todo.md            — 진행/완료 이동 + 날짜
```

"진행/완료 이동"이라는 서술은 **태스크 체크박스 목록**을 가리키는 것으로 읽힌다. BACKLOG 표는
같은 파일 안의 **별개의 표**인데, 이 문구로는 그것까지 대상인지 알 수 없다.

스캐폴드 자신도 같은 구조다 — `.claude/workspace/todo.md:10-25`가 체크박스 목록,
`:29-34`가 `| ID | 제목 | 상태 | spec/plan |` 표다. **파생 프로젝트 고유 문제가 아니다.**

### 이 문제의 진짜 층위

이 레포는 같은 실패를 이미 한 번 겪었다. `2026-07-27-version-release-harness-design.md:21`:

> 느슨한 원인은 "버전 체계가 없어서"가 아니라 **`readme-sync.md`의 자동 갱신 묶음 3번
> (changelog)이 강제되지 않아서**다.

그때의 처방은 문장 보강이 아니라 `check-docs.sh` §5(changelog 스테일 검사)라는 **기계 장치**였다.
이번 건도 구조가 같다. 목록에 8번째 줄을 더하는 것만으로는 이미 한 번 안 통한 처방을 반복한다.

**목표**: (1) 룰에서 BACKLOG 표를 명시적 갱신 대상으로 승격하고, (2) 룰이 지켜지지 않아도
기계가 잡도록 `check-docs.sh` §7을 신설한다. 룰은 의도를 적고, 검사는 결과를 본다.

## 요구사항 연결

이 레포는 스캐폴드 자신이라 REQ/FR 문서가 플레이스홀더 상태다(`01-*-requirements.md`는
대상 프로젝트가 채우는 골격). 따라서 REQ/FR 발번 없이 `BACKLOG-003` · `DEC-015`로만 추적한다.
검증은 `scripts/test-check-docs.sh`의 회귀 케이스가 담당한다.

## 설계

### ① 룰 변경 — `.claude/rules/readme-sync.md`

갱신 묶음을 7 → 8항목으로 늘린다.

```
1. .claude/docs/01-impl-requirements.md — 구현 현황 요약 표 (✅/⚠️/❌)
2. .claude/workspace/todo.md            — 진행/완료 이동 + 날짜
3. .claude/workspace/todo.md            — 관련 BACKLOG 행의 상태·근거 (해당 항목이 있을 때)
4. .claude/workspace/changelog.md       — 상세 이력 추가
5. README.md                            — Features/Changelog/Config (사용자 영향 시)
6. docs/user-guide.md                   — 실제 동작 근거로 갱신
7. .claude/docs/02-architecture.md      — 구조(정적)가 바뀐 경우만
8. docs/how-it-works.md                 — 큰 기능의 동작 흐름(동적)이 바뀐 경우만
```

목록 아래 "6·7은 조건부다" → "7·8은 조건부다". 절 두 개를 추가한다.

- **"3번이 왜 2번과 따로 있나"** — 같은 파일이지만 다른 표라는 것, 합치면 변경이 무의미해지는
  이유, 닫을 때 **근거 한 줄**(커밋 해시나 확인 방법)을 남긴다는 것.
- **"이 체크리스트로 막을 수 없는 것"** — 다른 작업의 부수 효과로 해소되는 항목은 완료 시점
  체크리스트에 걸리지 않는다. 주기적으로 문서가 아니라 **코드·실행에 대고** 전수조사한다.

**2번과 3번을 합치지 않는다.** 체크리스트는 줄 단위로 소비된다 — 절 안의 종속절은 건너뛰기
쉽고 별도 줄은 그렇지 않다. 이게 이 변경의 전부이므로 합치는 순간 변경이 무의미해진다.

### ② BACKLOG 표 스키마 — 4열 유지, 의미 확장

`spec/plan` 열을 `근거` 로 넓힌다. 완료일은 상태 칸에 괄호로 적는다.

```markdown
| ID | 제목 | 상태 | 근거 |
|----|------|------|------|
| BACKLOG-001 | 글로벌 룰 버전 관리 | ⏳ 대기 | DEC-014 |
| BACKLOG-002 | 버전·changelog 정합성 harness | ✅ 완료(2026-07-27) | `2026-07-27-version-release-harness-design.md` |
```

열 수를 유지하므로 이미 표를 가진 파생 프로젝트의 마이그레이션 비용이 없고, 대기·진행 행에
빈 칸이 생기지 않는다. `근거`에는 spec/plan 파일명·커밋 해시·확인 방법 중 무엇이든 들어간다.

### ③ `check-docs.sh` §7 — BACKLOG 상태 정합성

기존 §1~§6과 같은 자리(§6 뒤, 결과 집계 앞)에 인라인으로 넣는다. `lib-version.sh`에 두지
않는다 — 그 파일은 버전·changelog 조회 전용이고 헤더가 "순수 조회만 한다"고 규정한다.

**스킵 조건**: `.claude/workspace/todo.md`가 없거나 `| BACKLOG-NNN |` 형태의 표 행이 0개면
검사 자체를 건너뛴다. BACKLOG를 쓰지 않는 프로젝트에 경고를 만들지 않는다.

**완료 판정**: 표 행의 상태 칸(3번째 필드)에 `✅` 또는 `완료`가 있으면 완료. 단 `미완료`는
제외한다.

| 신호 | 판정 | 잡는 사고 |
|------|------|-----------|
| A | changelog의 **릴리즈된 구간**에 언급된 `BACKLOG-NNN`인데 표 행이 미완료 | 릴리즈까지 끝났는데 표가 진행중 (mobius4에서 실제로 난 사고) |
| B | `- [x]` 완료 체크박스 줄에 언급된 `BACKLOG-NNN`인데 표 행이 미완료 | 한 파일 안에서의 자기모순 |
| C | 문서가 참조한 `BACKLOG-NNN`이 표에 정의돼 있지 않음 | 표에서 조용히 사라진 항목 |

- **릴리즈된 구간**: changelog에서 첫 `^##\s+v?X.Y.Z` 헤딩 이후 전부. `[Unreleased]`는 제외한다
  — 작업 중에 ID를 적어두는 것은 정상이고, 그걸 경고로 만들면 작업 내내 시끄럽다.
  구간 판정은 `lib-version.sh`의 `CHANGELOG_PATH`와 `changelog_latest_release()`가 이미 쓰는
  헤딩 패턴을 그대로 재사용한다.
- **B의 신호를 `- [x]` 줄로 잡는 이유**: `## ✅ 완료` 같은 섹션 제목은 프로젝트마다 다르지만
  완료 체크박스는 마크다운 공통 표기다. 섹션 제목에 의존하면 파생 프로젝트에서 조용히
  무력화된다.
- **C의 파일 집합**: §4(DEC 댕글링)와 **동일한 집합·동일한 제외 규칙**(코드펜스 `strip_fences`,
  인라인 코드 `strip_inline_code`)을 쓴다. `docs/superpowers/`는 스캔하지 않는다.

경고 문구는 기존 `warn()`을 쓰므로 로컬 Stop hook에서는 비차단 경고, CI `--strict`에서는
차단이라는 기존 강제 모델을 그대로 따른다(새 개념을 늘리지 않는다).

### ④ 스캐폴드 자기 문서 반영

- `todo.md` — 표 헤더를 `근거`로, 기존 2행을 새 표기로 옮김. 이번 작업을 `BACKLOG-003`으로 등록.
- `changelog.md` `[Unreleased]` — 이번 변경 기록.
- `README.md` — §7을 검사 목록에 반영(README:177 부근의 `todo.md` semantics 줄 포함).
- `.claude/rules/commands.md` — `check-docs.sh` 설명 줄에 §7 추가.

## 검토한 대안

1. **룰 문장만 고친다 (요청서 원안)** — ❌ 기각. 이 레포가 changelog 건에서 이미 실패한 처방이다.
   근거는 위 "이 문제의 진짜 층위".
2. **2번 문구를 "태스크 목록 + BACKLOG 표"로 확장하고 항목 수를 7로 유지** — ❌ 기각. 체크리스트
   소비 단위가 줄이라 종속절은 건너뛰기 쉽다.
3. **표를 5열로 늘려 완료일을 독립 컬럼으로** — ❌ 기각. 대기·진행 행이 항상 비고, 이미 표를
   가진 파생 프로젝트가 열을 맞춰야 한다.
4. **`/audit-backlog` 명령 신설** — ❌ 이번 범위 제외(YAGNI). §7이 사고 유형의 상당 부분을
   자동으로 잡으므로, 남는 부분의 크기를 보고 나중에 정한다. 산문 경고로만 남긴다.
5. **§7-A를 `[Unreleased]` 포함 전 구간으로** — ❌ 기각. 작업 중 ID 언급이 정상이라 오탐이 상시화된다.

## 리스크 / 고려사항

- ~~**§7-A 오탐**: changelog에 "착수했다"는 뜻으로 BACKLOG ID를 적는 습관이 있으면 릴리즈 후
  경고가 뜬다. 알려진 한계로 스크립트 주석과 룰에 명시한다.~~
  → **구현 중 해소(DEC-016).** 이 오탐은 "알려진 한계"가 아니라 **스캐폴드 자신의 v0.1.0
  changelog에서 첫 실행에 바로 재현됐다**(`- **docs**: … BACKLOG-001로 기록.`). 릴리즈된
  구간 전체가 아니라 **`feat`·`fix` 항목의 언급만** 완료 신호로 보도록 좁혀 해소했다.
  남는 한계: BACKLOG를 `docs:` 항목으로만 닫는 작업은 A가 놓치고 B(완료 체크박스)가 잡는다.
- **§7-C 범위**: `docs/superpowers/`를 스캔하지 않으므로 spec/plan 머리말의 댕글링 BACKLOG
  참조는 잡지 못한다. 템플릿(`_TEMPLATE-*`)의 플레이스홀더를 제외하는 새 규칙이 필요해지는데,
  그 비용이 얻는 것보다 크다고 판단했다.
- **파생 프로젝트 전파**: 스캐폴드에 "이미 만든 프로젝트로 변경을 내려보내는 절차"가 없다
  (README 전수 확인, 관련 서술 0건). 파생 프로젝트가 스캐폴드 버전을 추적하지도 않는다.
  이 변경 자체보다 큰 문제일 수 있으나 **이번 사이클 범위 밖**이다.
- **릴리즈**: 이번 사이클에서 버전을 끊지 않는다. `[Unreleased]`에만 쌓는다.
