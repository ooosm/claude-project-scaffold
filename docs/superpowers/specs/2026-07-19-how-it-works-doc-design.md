# 설계: How It Works 문서(동작 원리 · 납품용)

## 문제 / 목표

큰 기능 단위로, 다양한 트리거(사용자 요청·시스템 이벤트·스케줄·웹훅)에서 내부 컴포넌트가
어떻게 상호작용하는지를 흐름도로 설명하는 납품 문서가 스캐폴드에 없었다. 납품 주고받는
쪽의 동작 이해를 돕는 것이 목적. architecture(정적 구조)와 상보적인 동적 흐름 뷰를 추가한다.

## 요구사항 연결

- 방법론 룰/문서 확장(코드 아님) → REQ/FR 신규 없음.

## 설계

- **위치**: `docs/how-it-works.md` (사람용 납품 문서 → 숨김 폴더 밖, DEC-005 논리 계승).
- **형식**: Mermaid(GitHub 렌더링·텍스트 diff·무의존). 기능/트리거당 1섹션 = 다이어그램 + 평문 워크스루 + FR/REQ 상호 링크.
- **타이밍(3단)**: ① lazy 생성(흐름 설명이 필요한 첫 큰 기능 완료 시) ② 조건부 갱신(큰 기능 흐름 변경 시만, architecture "구조 변경 시만"과 동형) ③ 릴리즈 시 일치성 검증.
- **연동**: readme-sync 갱신 묶음 7번(조건부)·업데이트 트리거·릴리즈 절차, requirements 상호 링크, CLAUDE.md·README·project-init 문서 분류, check-docs 플레이스홀더 대상.

## 검토한 대안

- 위치: **docs/**(채택) vs .claude/docs/03-*(기각: 납품 문서를 숨김 폴더에) — DEC-009.
- 타이밍: **lazy+조건부+릴리즈검증**(채택) vs 부트스트랩 선작성(기각: 추측 문서, 실제근거 원칙 위반).
- 다이어그램: **Mermaid**(채택) vs ASCII/외부도구(기각: 렌더링·diff·이식성).

## 리스크 / 고려사항

- 매 태스크 갱신으로 비대해질 위험 → "큰 기능 흐름"으로 트리거 게이트.
- 글로벌 미러링 대상 아님(문서 골격은 스캐폴드 고유). 룰 변경분(readme-sync 등)은 향후 글로벌 동기화 시 반영.
