# 결정 로그 (Decision Log)

> 모든 설계·구현 결정의 누적 로그. **append-only** — 새 항목은 항상 파일 끝에 추가하고,
> 과거 항목은 다시 쓰지 않는다. 번호는 마지막 DEC 번호 +1.
> 상세 규칙: `.claude/rules/decisions.md`. 큰 아키텍처 결정은 `ADR-NNN`으로도 남긴다.
>
> ⚠️ **새 프로젝트에 이 스캐폴드를 적용할 때**: 아래 DEC 항목들은 스캐폴드 레포 **자체의**
> 결정 이력(형식 예시 겸용)이다. 적용 시 전부 비우고 대상 프로젝트의 DEC-001부터 시작한다.

## DEC-001: 프로젝트 방법론으로 claude-project-scaffold 스캐폴드 채택 (2026-06-30)

**맥락**: 새 프로젝트 시작 시 결정 추적·요구사항 관리·문서 동기화가 매번 임기응변으로
이뤄져 일관성이 떨어졌다. 재사용 가능한 골격이 필요했다.

**결정**: `.claude/`(영구) + `docs/superpowers/`(작업 단위) 구조를 가진 템플릿 레포를
복사해 신규 프로젝트를 시작한다.

**검토한 대안**:
- ✅ **채택: 스캐폴드 템플릿 레포(방법 B)** — 이유: 이식성 높고 팀/타 머신 공유 가능. 복사 한 번으로 전체 규약이 따라온다.
- ❌ 기각: 글로벌 룰만 사용(방법 A) — 이유: 강력하지만 머신·계정에 묶여 팀 공유·이식이 어렵다(보완재로 병행은 가능).
- ❌ 기각: 문서 한 장(METHODOLOGY.md)만(방법 C) — 이유: 사람이 따라야 해서 강제력이 약하고 파일 구조가 자동 생성되지 않는다.

**성능·향후 영향**: 신규 프로젝트 초기화 시간 단축, 결정/요구사항 추적 일관성 확보.
룰이 바뀌면 템플릿을 갱신해 재배포해야 하는 유지보수 비용이 생긴다.

**출처**: 방법론 가이드(방법 A/B/C) — 이 템플릿의 `README.md`.

## DEC-002: 글로벌 룰 충돌을 "병합 + 우선순위 선언"으로 해소 (2026-07-18)

**맥락**: `~/.claude/rules/`에 이 스캐폴드의 구버전 룰 5종이 남아 있어, 스캐폴드 프로젝트에서
글로벌 룰과 프로젝트 룰이 동시에 로드되며 충돌했다(예: plan 산출물 경로가
`.claude/workspace/plan.md` vs `docs/superpowers/plans/`로 상이).

**결정**: README §대안 1 절차대로 글로벌 룰을 스캐폴드 최신판으로 병합하고, 글로벌
`CLAUDE.md` 상단에 "프로젝트 룰이 있으면 프로젝트 룰 우선" 선언을 추가한다.

**검토한 대안**:
- ✅ **채택: 병합 + 우선순위 선언** — 이유: 신규 프로젝트는 글로벌만으로 방법론을 상속하고, 스캐폴드 프로젝트는 충돌 없이 프로젝트 룰이 정본이 된다.
- ❌ 기각: 글로벌 룰 삭제 — 이유: 스캐폴드를 안 쓰는 프로젝트가 방법론을 잃는다.
- ❌ 기각: 현상 유지 — 이유: 근사-중복 룰 이중 로드는 지시 준수율을 떨어뜨리는 최악의 형태.

**성능·향후 영향**: 룰 개정 시 스캐폴드(정본)를 먼저 고치고 글로벌에 미러링해야 하는
동기화 비용이 생긴다(정본 방향: 스캐폴드 → 글로벌).

**출처**: 2026-07-18 스캐폴드 점검 리포트, README §부록 대안 1.

**검토한 대안**:

- ❌ 기각: `.claude/docs/03-commands.md` — 이유: docs/는 요구사항·아키텍처 등 산출물 문서 계열. 명령어는 룰(작업 방식)과 함께 로드되는 편이 실용적.

**성능·향후 영향**: "방법론 룰 8종 + commands.md" 구분을 문서에 유지해야 한다.

## DEC-004: 문서 정합성 검사를 스크립트 동봉 + hook은 opt-in으로 (2026-07-18)

**맥락**: 상태 정보가 여러 문서에 분산되어 있고 동기화가 전적으로 에이전트 성실성에
의존한다. 기계적 강제 수단이 필요하다.

**결정**: `scripts/check-docs.sh`(플레이스홀더 잔존·REQ/FR 상호 참조·DEC 번호 검사)를
동봉하고, 기본은 수동/체크리스트 실행. Stop hook 연결은 선택 사항으로 문서화만 한다.

**검토한 대안**:
- ✅ **채택: 스크립트 + opt-in hook** — 이유: 대상 프로젝트 환경(경로·셸)을 모르는 상태에서 hook을 기본 활성화하면 오작동 시 모든 세션을 방해한다. 스크립트는 어디서든 안전.
- ❌ 기각: Stop hook 기본 활성 — 이유: 실패 시 세션 종료마다 잡음, brownfield에서 경로 불일치 위험.
- ❌ 기각: 룰 텍스트만으로 유지 — 이유: 점검에서 확인된 핵심 약점(프롬프트 의존)을 방치.

**성능·향후 영향**: 검사 항목이 늘면 스크립트를 함께 유지보수해야 한다. `--strict`로 CI
연결 여지를 남김.

**출처**: 2026-07-18 스캐폴드 점검 리포트 §3.

## DEC-005: 사용자 가이드를 `docs/user-guide.md`로 이동 (2026-07-18)

**맥락**: 사용자 가이드는 사람(고객·팀원)에게 전달되는 납품 문서인데 숨김 폴더
`.claude/docs/`에 있어 가시성이 낮고, 납품 시 `.claude/` 제외와 함께 누락될 위험이 있다.

**결정**: `10-user-guide.md`를 `docs/user-guide.md`로 이동한다. 요구사항·아키텍처 문서는
에이전트 운영 산출물로 보고 `.claude/docs/`에 유지한다.

**검토한 대안**:
- ✅ **채택: 사용자 가이드만 `docs/`로 이동** — 이유: 사람이 읽는 납품물과 에이전트 산출물의 경계가 명확해진다.
- ❌ 기각: `.claude/docs/` 유지 — 이유: dot-폴더는 GitHub·납품 패키징에서 잘 보이지 않는다.
- ❌ 기각: 요구사항 문서까지 전부 이동 — 이유: REQ/FR은 에이전트가 상시 갱신하는 운영 문서 성격이 강함. 납품 요구 시 그때 내보내면 된다.

**성능·향후 영향**: readme-sync 갱신 묶음·CLAUDE.md·README의 경로 참조를 함께 관리해야
한다(이번에 일괄 갱신).

**출처**: 2026-07-18 스캐폴드 점검 리포트 §5.

## DEC-006: 로컬 Stop hook은 비차단(경고), 차단은 CI(strict)가 담당 (2026-07-18)

**맥락**: DEC-004에서 Stop hook을 opt-in으로 두었으나, "얕은 harness" 승격 요구에 따라
문서 정합성 검사를 실제로 배선해야 한다. 다만 로컬에서 하드 차단하면 이질적 프로젝트·
빠른 작업에서 거슬리고, 대상 프로젝트에 복사될 때 경로 불일치로 오작동할 수 있다.

**결정**: 로컬 Stop hook은 `check-docs.sh`를 **비차단(경고, exit 0)**으로 실행하고
(스크립트 부재 시 무해 통과하도록 `[ -f … ] && … || true` 가드), 실제 **차단은 CI에서
`--strict`**로 수행한다. DEC-004의 opt-in 방침을 "비차단 기본 배선"으로 갱신한다.

**검토한 대안**:
- ✅ **채택: 로컬 비차단 + CI strict** — 이유: 로컬은 부드럽게(잡음·오작동 없음), 병합 지점은 엄격하게. harness의 강제와 스캐폴드의 이식성을 모두 만족.
- ❌ 기각: 로컬 Stop hook 차단(strict) — 이유: 빠른 작업 방해, 대상 프로젝트 경로 불일치 시 세션 종료마다 실패.
- ❌ 기각: opt-in 유지(DEC-004 그대로) — 이유: "얕은 harness" 승격 요구를 충족하지 못함(강제 미배선).

**성능·향후 영향**: 로컬에서 문서 오류를 놓쳐도 CI가 최종 방어선이 된다. CI가 유일한
하드 게이트이므로 워크플로 유지보수가 중요해진다.

**출처**: 2026-07-18 얕은 harness 설계(`docs/superpowers/specs/2026-07-18-thin-harness-spine-design.md`), DEC-004 갱신.

## DEC-007: 슬래시 커맨드를 헬퍼 스크립트로 구현해 원자성·결정론 확보 (2026-07-18)

**맥락**: `/dec`·`/new-feature`를 harness 동사로 만들려면, 순수 프롬프트 템플릿만으로는
DEC 번호 할당이 비결정적이고(에이전트가 손으로 셈 → 병렬 세션 충돌), spec/plan 생성도
매번 미묘하게 달라진다.

**결정**: 슬래시 커맨드는 **헬퍼 스크립트를 호출**한다. `new-dec.sh`가 단일 프로세스로
번호 계산+append를 수행해 **원자적 번호 할당**을 보장하고, `new-feature.sh`가 오늘 날짜로
spec/plan 골격을 결정론적으로 생성한다. 커맨드 본문은 스크립트 실행 + 산출물 채우기 안내만 담는다.

**검토한 대안**:
- ✅ **채택: 슬래시 커맨드 → 스크립트 호출** — 이유: 원자성·결정론 확보, 번호 충돌(점검 §4에서 지적)을 예방(탐지가 아니라).
- ❌ 기각: 순수 프롬프트 커맨드 — 이유: 번호 계산·파일 생성이 에이전트 재량이라 drift·충돌 재발.
- ❌ 기각: 인라인 `!`bash 확장에만 의존 — 이유: 확장 시점·allowed-tools 의존성이 커 이식성/견고성이 낮음. 에이전트가 Bash 도구로 실행하는 편이 견고.

**성능·향후 영향**: 새 harness 동사를 추가할 때 "스크립트 + 얇은 커맨드 래퍼" 패턴을
재사용한다. 스크립트 이식성(BSD/GNU)을 유지보수해야 한다(`sed -i.bak` 사용).

**출처**: 2026-07-18 얕은 harness 설계 spec, 점검 리포트 §3·§4.

## DEC-008: 위험도 기반 하이브리드 브랜치 전략을 방법론 룰로 규정 (2026-07-19)

**맥락**: 1인 개발에서 브랜치 전략 규칙이 없어, "항상 브랜치+PR"(과잉 의식) 또는
"항상 메인"(메인 불안정) 중 하나로 치우치기 쉬웠다. 방금 만든 harness 게이트 철학
(로컬 soft / 병합 strict)과 브랜치 전략을 연결할 규범이 필요했다.

**결정**: `.claude/rules/git-workflow.md`(신규, 방법론 룰 9번째)에 **위험도 기반 하이브리드**를
규정한다 — 안전 변경(문서·설정·소규모)은 메인 직접, 위험/장기/배포/게이트/병렬 작업은
브랜치+PR. PR을 harness 게이트로 명시(브랜치 보호로 strict CI를 자문→차단 승격).

**검토한 대안**:
- ✅ **채택: 위험도 하이브리드(전용 룰 파일)** — 이유: 안전 변경은 빠르게, 위험 변경은 격리. 발견성·응집성 위해 전용 파일.
- ❌ 기각: "항상 브랜치+PR" 단일 규칙 — 이유: 문서 한 줄 수정에도 PR 의식이 과함. 솔로는 self-approval이라 리뷰 효과도 약함.
- ❌ 기각: "항상 메인" 단일 규칙 — 이유: 배포/위험 변경에서 메인이 깨지고, CI가 사후 통보에 그쳐 게이트가 안 됨.
- ❌ 기각: conventions.md에 흡수 — 이유: 브랜치 전략·PR 게이트는 네이밍 규약보다 독립 주제. 별도 파일이 발견성 높음.

**성능·향후 영향**: 방법론 룰이 8→9종이 되어 "8종" 표기를 일괄 갱신해야 했다(과거 DEC는
append-only라 제외). 글로벌 룰(`~/.claude`)과 divergence가 생기므로 미러링(DEC-002 방향)은
사용자 승인 후 별도 수행한다.

**출처**: 2026-07-19 브랜치 전략 논의, spec `2026-07-19-git-workflow-rule-design.md`.

## DEC-009: How It Works 문서를 docs/에 배치하고 lazy+조건부+릴리즈검증으로 관리 (2026-07-19)

**맥락**: 큰 기능 단위로 트리거별 컴포넌트 상호작용(동작 원리)을 흐름도로 설명하는 납품
문서가 없었다. 납품 주고받는 쪽의 이해를 돕는 용도로, 기존 architecture(정적 구조)와 겹치지
않게 배치·관리 규칙을 정해야 했다.

**결정**: `docs/how-it-works.md`(사람용 납품 문서)를 신설한다. Mermaid로 그리고,
**lazy 생성(흐름 설명이 필요한 첫 큰 기능 완료 시) + 조건부 갱신(큰 기능 흐름 변경 시만) +
릴리즈 시 일치성 검증**의 3단으로 관리한다. architecture는 정적 구조, how-it-works는 동적
흐름으로 역할을 분리하고 상호 링크한다.

**검토한 대안**:
- ✅ **채택: `docs/` 배치 + lazy/조건부/릴리즈검증 + Mermaid** — 이유: 납품 문서는 숨김 폴더 밖에(DEC-005 계승), 추측 문서화 방지, GitHub 렌더링·diff 용이.
- ❌ 기각: `.claude/docs/03-how-it-works.md` — 이유: 납품 대상 문서를 숨김 폴더에 두면 납품 시 `.claude/` 제외와 함께 누락 위험.
- ❌ 기각: 부트스트랩에 선작성 — 이유: 동작이 없어 추측 문서가 됨("실제 구현 근거" 원칙 위반).
- ❌ 기각: ASCII/외부 다이어그램 도구 — 이유: 렌더링·텍스트 diff·무의존성에서 Mermaid가 우위.

**성능·향후 영향**: 갱신 트리거를 "큰 기능 흐름"으로 좁혀 비대화를 막는다. readme-sync 갱신
묶음이 7개 항목(6·7 조건부)이 되었다. 문서 골격은 스캐폴드 고유라 글로벌 미러링 대상이
아니며, 룰 변경분(readme-sync 등)은 향후 글로벌 동기화 시 함께 반영한다.

**출처**: 2026-07-19 how-it-works 논의, spec `2026-07-19-how-it-works-doc-design.md`.

## DEC-010: check-docs 플레이스홀더 검출을 비-ASCII 대괄호 + Mermaid 펜스 제외로 재설계 (2026-07-27)

**맥락**: 실사용 피드백 — check-docs 플레이스홀더 정규식이 4개 패턴만 봐서 `[설치 명령]`·
`[한두 줄: …]`·`VAR_NAME`을 통과시켜 **거짓 초록불**을 6번 냈고, 사용자 가이드 미작성을
게이트가 잡지 못했다. 검출을 넓히면 마크다운 링크·체크박스·코드 인덱싱·Mermaid 노드
라벨에서 오탐 위험이 커진다.

**결정**: 플레이스홀더를 **비-ASCII 문자를 포함한 대괄호**(`\[[^]]*[^ -~][^]]*\]`) + `VAR_NAME`·
날짜/시간·ID 리터럴로 검출하고, `LC_ALL=C`로 로케일 독립성을 확보한다. `docs/how-it-works.md`의
Mermaid 노드 라벨(비-ASCII 대괄호)은 ```mermaid 펜스를 빈 줄 치환(행번호 보존)해 제외한다.
회귀 테스트 `scripts/test-check-docs.sh`를 추가해 CI에서 강제한다.

**검토한 대안**:
- ✅ **채택: 비-ASCII 대괄호 + Mermaid 펜스 제외 + 회귀 테스트** — 이유: 스켈레톤 플레이스홀더는 전부 한글(비-ASCII)을 포함하고, ASCII 정상표기(체크박스·[Unreleased]·arr[idx])는 자연히 제외된다. 테스트로 회귀 고정.
- ❌ 기각: 명시적 어휘 allowlist 확장 — 이유: 피드백이 지적한 "빠뜨림"이 새 플레이스홀더마다 재발.
- ❌ 기각: 한글 범위 `[가-힣]` — 이유: 비-UTF-8 로케일(CI) 에서 불안정.
- ❌ 기각: 전체 코드펜스 제외 — 이유: `[설치 명령]`이 ```bash 펜스 안이라 놓친다. Mermaid 펜스만 제외.

**성능·향후 영향**: 검출이 넓어져 대상 프로젝트의 미완성 납품 문서를 실제로 잡는다(로컬 경고/
CI 차단). check-docs가 이제 회귀 테스트를 갖춘 첫 스크립트 — 검출 규칙 변경 시 테스트를 함께
갱신한다. 검출 규칙은 스캐폴드 고유라 글로벌 미러링 대상이 아니다.

**출처**: 2026-07-27 실사용 피드백, spec `2026-07-27-check-docs-placeholder-hardening-design.md`.

## DEC-011: 버전·changelog 정합성을 check-docs 확장 + /release 동사로 강제 (2026-07-27)

**맥락**: 스캐폴드에 릴리즈 절차(`readme-sync.md` §릴리즈 절차)는 문서로 있으나 강제 장치가
없었다. 이 레포 자신의 히스토리가 그 결과를 보여준다 — `/dec` + 번호 검사가 걸린 decision-log는
6개 커밋에서 갱신되어 DEC-001~010이 쌓인 반면, harness가 없는 changelog는 초기 커밋 이후
0회 갱신(골격 그대로)이고 git tag는 0개였다. 규칙 문서를 더 쓰는 걸로는 고쳐지지 않는다는 것이
확인된 상태에서, 버전 관리를 스캐폴드 범위로 볼지와 어떤 장치를 둘지 결정이 필요했다.

**결정**: 버전 관리를 스캐폴드 범위로 편입하고, 새 개념을 늘리지 않은 채 기존 harness 척추
(스크립트 + 슬래시 커맨드 + check-docs + Stop hook/CI)에 얹는다 — `lib-version.sh`(SoT 감지),
`check-docs.sh` §4·§5(changelog 스테일·버전 3자 일치), `/release`(파일 변경까지만).

**검토한 대안**:

*버전 SoT*
- ✅ **채택: 매니페스트 우선 + `VERSION` 폴백** — 이유: `package.json` 등이 있으면 그것이 이미
  SoT다. 별도 파일을 더하면 이중 관리가 되어 드리프트하는데, 그건 이 harness가 없애려는 문제다.
- ❌ 기각: 항상 별도 버전 파일 — 이유: 파싱은 가장 단순하나 Node/Python 프로젝트에서 매니페스트와
  이중 관리가 되고, 그 불일치를 잡는 검사가 또 필요해진다.
- ❌ 기각: `.claude/version.json` 전용 파일 — 이유: `npm publish`·`poetry build` 등 배포
  툴체인이 이 파일을 못 읽어 결국 매니페스트와 이중 관리가 된다.

*정책 판단*
- ✅ **채택: 자동 감지 + `commands.md` 한 줄 override** — 이유: 부트스트랩 때 아무것도 안 해도
  동작하고, 오탐이 나면 그때 한 줄 추가한다. 새 파일을 늘리지 않는다.
- ❌ 기각: 순수 자동 감지만 — 이유: `private: true` + `0.0.0` 고정 내부 서비스에서 경고를 끌
  방법이 없어 영구 오탐이 된다.
- ❌ 기각: 명시 선언 필수 — 이유: 스캐폴드 복사 직후부터 미선언 경고가 떠 첫인상이 나쁘다.

*changelog 스테일 판정*
- ✅ **채택: git 히스토리 기반 + 유예 3건** — 이유: 작업 중 연속 커밋에 숨 쉴 틈을 주면서, 이
  레포가 실제로 빠졌던 패턴(기능 커밋 누적·갱신 0회)은 확실히 잡는 임계값이다.
- ❌ 기각: 유예 없음(1건) — 이유: 룰 문자와는 정확히 일치하나 중간 체크포인트 커밋마다 경고가
  떠 피로도가 높고, strict CI에서 머지가 자주 막힌다.
- ❌ 기각: diff 기반 — 이유: 로컬(워킹트리)과 CI(PR base 대비)의 판정 기준이 달라 동작 경로가
  둘로 갈리고 테스트도 두 벌이 된다.
- 부기: `[Unreleased]`가 비었는지는 신호로 쓰지 않는다 — 릴리즈 직후엔 정상적으로 비어 있어
  매 릴리즈마다 오탐이 난다.

*`/release` 범위*
- ✅ **채택: 파일 변경까지만(커밋·태그는 명령어 출력만)** — 이유: `git-workflow.md`의 "커밋·
  푸시는 사용자가 요청할 때"와 일치하고, `new-dec.sh`의 관용구(골격만 만들고 판단이 필요한
  내용은 에이전트가 채움)를 그대로 따른다. git 부작용이 없어 되돌리기 쉽다.
- ❌ 기각: 커밋+태그 자동 — 이유: README 요약을 사람이 채우기 전에 커밋되고, 태그는 푸시하면
  되돌리기 어렵다.
- ❌ 기각: 2단계 `--finalize` — 이유: 가장 안전하나 단계가 늘고, finalize를 빠뜨리면 버전만
  오르고 태그가 없는 반준비 상태로 남는다.

*코드 경계*
- ✅ **채택: `lib-version.sh` 공유 + 검사는 `check-docs.sh` 인라인** — 이유: "check-docs 통과"
  문구가 `settings.json`·CI yml·`commands.md`·`validation.md`·README·`CLAUDE.md` 6곳에 박혀
  있어 진입점 1개 유지가 배선 안정성에 결정적이다. 감지 로직은 lib로 빼서 중복이 0이다.
- ❌ 기각: `check-version.sh` 별도 진입점 — 이유: 책임 분리는 깔끔하나 배선 6곳을 고쳐야 하고,
  진입점이 둘이면 하나를 빼먹고 안 돌릴 위험이 생긴다.
- ❌ 기각: lib 없이 각 스크립트에 복붙 — 이유: SoT 감지 로직이 두 벌이 되어 드리프트한다.

*스캐폴드 자기적용*
- ✅ **채택: 전면 도그푸딩(VERSION 0.1.0 + changelog 백필 + v0.1.0 태그)** — 이유: 장치가 자기
  레포에서 즉시 검증되고, 대상 프로젝트가 "scaffold vX.Y.Z 기준으로 적용"을 기록할 수 있어
  BACKLOG-001(글로벌 룰 버전 관리)로 이어진다.
- ❌ 기각: changelog만 백필 — 이유: 버전 검사 경로가 자기 레포에서 한 번도 안 돌아 회귀
  테스트에만 의존하게 된다.
- ❌ 기각: 대상 프로젝트용 장치만 추가 — 이유: "룰만 있고 안 지켜진다"는 원래 문제가 스캐폴드
  레포에 그대로 남는다.

**성능·향후 영향**: `check-docs.sh`가 약 100줄에서 150줄로 늘어난다 — 더 커지면 별도 진입점
(기각한 B안)으로 분리하되 `lib-version.sh`는 그대로 재사용할 수 있게 순수 조회 함수로만 짰다.
§4가 git 히스토리를 읽으므로 CI에 `fetch-depth: 0`이 필요하고(`actions/checkout@v4` 기본은
depth 1), 스크립트는 shallow clone을 감지해 조용히 스킵한다. §4는 커밋 타입 표기에 의존하므로
`feat:`/`fix:` 오타는 미검출인데, 게이트의 목적이 실수 방지지 우회 봉쇄가 아니므로 감수한다.
`calver`는 형식 검사 제외와 명시 버전 인자만 지원한다 — 자동 bump 규칙이 필요해지면 그때 확장.

**출처**: 2026-07-27 사용자 문의(버전 관리가 느슨함), spec
`2026-07-27-version-release-harness-design.md`, BACKLOG-002.

## DEC-012: 브라운필드 적용 피드백 6건 중 harness 버그 4건 수정 (2026-07-27)

**맥락**: 실제 브라운필드 적용(`influencer-agency-automation`, 문서 4종·코드 0줄)에서 6건의
문제가 보고됐다. 6건 전부 재현·검증했고, 2건은 보고보다 문제가 컸다 — 배포되는
`.claude/CLAUDE.md`의 오탐은 11건이 아니라 14건이었고, 보고가 놓친 부류(파일명 규약
`YYYY-MM-DD-*-design.md`)가 하나 더 있었다. 이 중 스크립트로 고칠 4건을 먼저 처리한다
(절차 문서 2건은 별도 작업).

**결정**: `new-dec.sh` 말미 정규화 + `check-docs` 검출 규칙 재조정(코드펜스 전체 제외,
ID 리터럴에 한해 인라인 코드 제외) + DEC 댕글링 검사 신설. 각각 회귀 테스트를 함께 넣고,
`new-dec.sh` 전용 테스트 파일(`test-new-dec.sh`)을 CI에 추가한다.

**검토한 대안**:

*`new-dec.sh` 접합 버그 (모든 신규 프로젝트의 첫 `/dec`에서 100% 재현)*
- ✅ **채택: append 전 말미 정규화** — 이유: 뒤쪽 빈 줄·구분선을 걷어내고 항상 구분선 + 빈
  줄로 끝맺으므로 스크립트가 입력 상태에 무관해진다. 부트스트랩이 안내 주석을 지우든 말든,
  파일이 개행 없이 끝나든 동작이 같다. 재현 테스트를 먼저 써서 확인했다.
- ❌ 기각: `decision-log.empty.md`를 함께 배포하고 "교체하라"고 지시 — 이유: 근본 원인(앵커
  의존)이 남아, 사용자가 다른 방식으로 로그를 비우면 같은 버그가 재발한다.
- ❌ 기각: README에 "안내 주석을 반드시 남길 것" 명시 — 이유: 사람·에이전트의 성실성에
  의존하는 가장 약한 해법이고, harness의 존재 이유와 어긋난다.

*플레이스홀더 오탐 (규약 산문을 치환 대상으로 오인)*
- ✅ **채택: 코드펜스 전체 제외 + ID 리터럴에만 인라인 코드 제외** — 이유: 두 갈래로 나눠야
  했다. 백틱을 일괄 제외하면 스켈레톤 Configuration 표의 `VAR_NAME`처럼 **백틱 안에 있는
  진짜 플레이스홀더**를 놓친다. 그래서 대괄호·`VAR_NAME`·날짜는 펜스만 제외하고, ID
  리터럴만 백틱까지 제외한다. 14건 → 3건으로 줄었다.
- ❌ 기각: 백틱 일괄 제외(피드백의 원안) — 이유: 위와 같이 정탐을 잃고, 표 안의 맨몸
  `REQ-N-M` 3건은 어차피 안 잡혀 문제가 남는다.
- ❌ 기각: ID 리터럴 검사 자체를 삭제 — 이유: `01-impl-requirements.md`·`changelog.md`
  골격의 `DEC-NNN`은 실제 치환 대상이라 정탐을 통째로 잃는다.
- 남은 3건은 배포 `CLAUDE.md`의 맨몸 표기를 백틱으로 바꿔 해소했다. 피드백이 실제로 겪은
  `REQ-N-M` → `REQ-1-1 형식` 같은 품질 저하와 달리, 백틱은 ID 규약 표기로 오히려 정확한
  조판이라 의미 손실이 없다.

*DEC 댕글링 참조*
- ✅ **채택: check-docs에 검사 신설 + 룰 본문의 실제 참조 제거(둘 다)** — 이유: 검사만 넣으면
  복사 직후 경고가 뜨고, 참조만 지우면 앞으로 생길 같은 실패를 못 잡는다. 코드펜스·백틱
  제외가 이미 갖춰져 형식 예시(`DEC-012`)는 자동으로 걸러진다 — 구현 비용이 거의 없었다.
- ❌ 기각: 룰에서 번호만 제거 — 이유: REQ/FR과 같은 실패 모드인데 검사가 없어 조용히 살아남는
  구조가 그대로 남는다.

*테스트 파일 분리*
- ✅ **채택: `test-new-dec.sh` 별도 파일 + CI 스텝 추가** — 이유: `test-check-docs.sh`에
  넣으면 파일명이 내용과 어긋난다. 검사 대상 스크립트가 다르므로 분리가 정직하다.
- ❌ 기각: `test-check-docs.sh`에 합치기 — 이유: 이름이 거짓말이 되고, 실패 시 어느 스크립트
  문제인지 즉시 안 보인다.

**성능·향후 영향**: `check-docs`의 검출이 두 갈래(펜스만 제외 / 펜스+백틱 제외)로 나뉘어
`scan_placeholders`가 두 번 스캔한다 — 문서 수십 개 규모에서 체감 차이는 없다. 코드펜스를
통째로 제외하므로 **펜스 안의 진짜 플레이스홀더는 이제 안 잡힌다**(예: 설치 명령 블록).
그 손실보다 원본 스키마·열거형을 그대로 옮길 수 있는 이득이 크다고 판단했고, 펜스 안
플레이스홀더는 대부분 템플릿 파일에 몰려 있어 어차피 검사에서 제외된다. DEC 댕글링 검사가
`.claude/rules/*.md`까지 스캔 대상에 넣으므로, 앞으로 룰 본문에서 DEC 번호를 인용하려면
백틱을 쓰거나 로그에 실제로 존재해야 한다.

**출처**: 브라운필드 적용 피드백 문서(2026-07-27, `influencer-agency-automation`), 6건 중
1·2·3·5번. 4·6번(절차 문서)은 후속 작업.

## DEC-013: brownfield 적용 절차를 2축 판별 + 경로 충돌 조정 0단계로 개정 (2026-07-27)

**맥락**: 실제 브라운필드 적용 피드백의 4·6번. 적용자가 보고한 **가장 큰 실제 비용**은 §B의
3분류(복사/병합/역설계) 어디에도 없는 네 번째 일이었다 — 기존 문서 체계와 스캐폴드가 **같은
역할에 다른 정본 경로**를 주장하는 충돌을 판정하는 일. 4건이 충돌했고 판정에만 30분 이상
들었는데 README에는 판단 근거가 전혀 없었다. 동시에 그 프로젝트는 "문서는 brownfield, 코드는
greenfield"(코드 0줄)라 §B가 유일한 큰 비용이라고 못박은 ③ 역설계가 통째로 무의미했고,
"기존 README는 유지"라는 지침도 틀렸다(README가 문서 체계 정의서였다).

**결정**: 판별을 **코드 축 / 문서 축 2축**으로 분리하고, §B에 **①보다 앞서는 ⓪ 경로 충돌
조정** 단계를 신설한다. ③ 역설계는 코드 축이 ✓일 때만 수행하도록 명시한다.

**검토한 대안**:

*정본 충돌 문제*
- ✅ **채택: ⓪ 단계 신설 + 판정 기준과 예외 조건을 함께 명시** — 이유: 판단이 필요한 일이라
  기계로 못 막는다. 대신 **무엇을 판정해야 하는지(역할 4종)와 어느 쪽이 유리한지(harness가
  하드코딩한 경로)**를 주면 30분짜리 고민이 몇 분으로 준다. "정하지 않고 넘어가는 것만이
  오답"이라고 못박아, 어느 쪽을 고르든 DEC로 남기게 했다.
- ❌ 기각: 경로를 설정 파일로 빼서 스크립트가 읽게 — 이유: harness 3개 스크립트에 경로 설정
  레이어를 도입하는 비용이 크고, 얕은 harness 철학에 어긋난다. 실제 적용 사례에서도 4건 중
  3건은 스캐폴드 경로를 그대로 채택했다 — 문제는 경로 유연성이 아니라 **판정 절차의 부재**였다.
- ❌ 기각: ①의 "그대로 복사해도 안전" 문구만 수정 — 이유: 경고는 되지만 무엇을 어떻게
  판정할지가 여전히 없어, 같은 30분을 다시 쓰게 된다.

*greenfield/brownfield 분류*
- ✅ **채택: 코드 축 / 문서 축 2축 매트릭스(4유형)** — 이유: ③ 역설계는 코드 유무가, ⓪ 경로
  충돌은 문서 유무가 결정한다. 두 축이 독립이므로 단일 축으로는 표현이 안 된다. "문서 선행형"은
  기획서를 먼저 쓰고 에이전트로 구현하는 워크플로에서 표준에 가까워, 이 스캐폴드의 사용자층과
  정확히 겹친다.
- ❌ 기각: 3번째 유형("문서 선행형")만 추가 — 이유: 4유형 중 하나만 특례로 넣으면 나머지
  조합(코드 ✓·문서 ✗)의 ⓪ 불필요가 여전히 안 드러난다. 축을 나누면 4유형이 자연히 유도된다.
- ❌ 기각: 기존 2분류 유지 + 주의문 — 이유: 판별표가 `README.md` 존재만으로 brownfield를
  확정하는 구조 자체가 원인이라 주의문으로는 안 고쳐진다.

**성능·향후 영향**: 코드 변경 0 — 문서만 바뀐다. ⓪이 복사 **전**에 오므로 적용 절차의 첫
단계가 "판단"이 됐다(기존엔 "복사"). 문서 축이 ✗인 프로젝트는 ⓪을 건너뛰므로 순수 greenfield
경로는 그대로다. 앞으로 harness가 새 경로를 하드코딩할 때마다(예: 버전 SoT·changelog) ⓪의
역할 표에 행을 추가해야 한다 — `readme-sync.md`의 갱신 묶음과 별개로 챙길 지점이다.

**출처**: 브라운필드 적용 피드백 문서(2026-07-27, `influencer-agency-automation`) 4·6번.
적용자가 "저자가 하나만 고친다면 4번"으로 지목한 항목. 1·2·3·5번은 DEC-012.

## DEC-014: 글로벌 룰 추적을 허용목록 방식으로 좁힘 (통째 추적 기각) (2026-07-27)

**맥락**: 2026-07-27 스캐폴드 → 글로벌 룰 미러링을 수행했으나 `~/.claude`가 git 미추적이라
변경 이력이 남지 않았다. BACKLOG-001은 원래 "`~/.claude`를 별도 git 레포로 분리·추적"으로
적혀 있었는데, 실행 직전에 디렉토리 내용을 실측하니 그 문구대로 하면 안 되는 것이 드러났다.

```
저작 파일(추적 대상)   약 64K   CLAUDE.md 4K · rules 44K · hooks 4K · statusline.sh 4K · settings.json 8K
도구 생성물            약 300M  projects 269M(대화 트랜스크립트) · file-history 18M ·
                                plugins 6.9M · uploads 4.4M · telemetry 1.4M · history.jsonl 288K …
```

비율이 약 1 : 4,700이다.

**결정**: `~/.claude`에서 **거부-기본(deny-by-default) 허용목록**으로 저작 파일만 추적한다.
BACKLOG-001 문구를 그렇게 고치고, 실행은 사용자 판단으로 보류한다(글로벌 폴더 현상 유지).

**검토한 대안**:
- ✅ **채택: `~/.claude`에서 git init + 허용목록 `.gitignore`** — 이유: 파일이 제자리에 있어
  심볼릭 링크의 취약함(도구가 링크를 따라가지 않고 파일을 교체할 위험)이 없다. `*` 로 전부
  막고 `!` 로 열므로 도구가 나중에 새 디렉토리를 만들어도 자동으로 빠진다 — 허용목록은
  **미래의 추가에 대해 안전한 방향으로 실패**한다.
- ❌ 기각: `~/.claude` 통째 추적(원래 BACKLOG-001 문구) — 이유: ⑴ `projects/`는 전체 대화
  트랜스크립트라 세션 중 붙여넣은 토큰·키·고객 데이터가 섞여 있을 수 있고, 원격에 한 번
  푸시하면 되돌리기 어렵다. ⑵ 매 세션 `projects/`·`history.jsonl`이 변해 트리가 항상
  더러워지므로 정작 보려던 룰 변경 diff가 노이즈에 묻힌다 — **이력을 남기려다 이력을 못 읽게
  된다.** ⑶ 300M이 계속 churn 하면 git이 느려진다.
- ❌ 기각: 별도 레포 + 심볼릭 링크(dotfiles 방식) — 이유: 격리는 가장 깔끔하나 `~/.claude`는
  Claude Code가 능동적으로 쓰는 디렉토리라, 도구가 링크를 교체해버리면 조용히 추적에서
  이탈한다. 실패가 눈에 안 보이는 쪽이라 기각.
- ❌ 기각: 글로벌을 아예 추적하지 않고 스캐폴드에서 재생성 — 이유: 검토했으나 성립하지
  않는다. DEC-002가 "스캐폴드 정본 → 글로벌 미러"로 규정했으니 파생물은 이력이 필요 없다는
  논리인데, **실제 글로벌 파일은 기계적 파생물이 아니다** — "글로벌 기본값" 헤더, 스캐폴드
  없는 프로젝트용 조건부 표현("`docs/user-guide.md`, 있는 경우"), 글로벌 전용 섹션
  (`readme-sync`의 README 기본 구조·업데이트 방식 예시)이 섞인 **저작 파생물**이라 재생성이
  불가능하다. 따라서 자체 이력이 필요하다.

**성능·향후 영향**: 추적 범위가 좁아 레포가 가볍고 diff가 룰 변경만 보여준다. 대신 두 가지
운용 규율이 필요하다 — **`git add -f` 금지**(허용목록을 우회한다), **원격 연결 전
`git ls-files` 로 추적 목록 육안 확인**. 도구가 향후 저작 파일을 새 경로에 두면(예: 새
`output-styles/`) 허용목록에 수동 추가해야 한다 — 빠뜨리면 추적이 안 될 뿐 유출은 없으므로
안전한 방향의 실패다. 이 결정은 스캐폴드 레포 자체에는 코드 영향이 없다(문서만 갱신).

**출처**: 2026-07-27 글로벌 룰 미러링 수행 후 사용자 문의, BACKLOG-001. 실행은 보류
(사용자 결정: 글로벌 폴더 현상 유지).

## DEC-015: BACKLOG 상태 정합성을 룰 문장 + check-docs §7 한 쌍으로 처리 (2026-08-05)

**맥락**: 파생 프로젝트에서 백로그를 코드에 대고 전수조사했더니 구현·릴리즈까지 끝난 항목이
표에 `진행중`으로 남아 있었다. 원인은 `readme-sync.md` 갱신 묶음 2번이 `todo.md`를
"진행/완료 이동"이라고만 적어, 같은 파일 안의 BACKLOG 표가 대상 밖으로 읽힌 것이다.
스캐폴드의 `todo.md`도 동일 구조라 물려주는 문제다. 개선 요청서는 룰 문장 수정만 제안했다.

**결정**: 룰에 갱신 묶음 항목을 하나 추가(7→8)하되, **동시에 `check-docs.sh` §7을 신설**해
BACKLOG 표의 상태 스테일을 기계적으로 잡는다.

**검토한 대안**:
- ✅ **채택: 룰 문장 + §7 검사 한 쌍** — 이유: 이 레포는 같은 실패를 이미 겪었다.
  `2026-07-27-version-release-harness-design.md:21`이 "느슨한 원인은 갱신 묶음 3번(changelog)이
  강제되지 않아서"라고 진단했고, 그때의 해법은 문장이 아니라 `check-docs` §5였다. 룰은 의도를
  적고 검사는 결과를 본다.
- ❌ 기각: 룰 문장만 수정(요청서 원안) — 이유: 목록에 있는데도 안 지켜진 것이 문제인데,
  같은 목록에 줄을 하나 더 얹는 처방이다. changelog 건에서 이미 안 통했다.
- ❌ 기각: 2번 문구 확장(항목 수 7 유지) — 이유: 체크리스트 소비 단위는 줄이다. 절 안의
  종속절은 건너뛰기 쉽고 별도 줄은 그렇지 않다.
- ❌ 기각: BACKLOG 표를 5열로(완료일 독립 컬럼) — 이유: 대기·진행 행이 항상 비고, 이미 표를
  가진 파생 프로젝트가 열을 맞춰야 한다. 4열 유지 + `spec/plan` → `근거` 의미 확장으로 해결.
- ❌ 기각: `/audit-backlog` 명령 신설 — 이유: YAGNI. §7이 사고 유형의 상당 부분을 자동으로
  잡으므로, 남는 부분(다른 작업의 부수 효과로 해소되는 항목)의 크기를 보고 나중에 정한다.

**성능·향후 영향**: §7은 grep 수준이라 검사 시간에 영향이 없다. 스킵 조건(BACKLOG 표 행 0개)이
있어 BACKLOG를 쓰지 않는 프로젝트에는 아무 영향이 없다. 알려진 한계 둘: (1) §7-A는 changelog에
"착수했다"는 뜻으로 ID를 적는 습관이 있으면 오탐한다, (2) §7-C는 `docs/superpowers/`를
스캔하지 않아 spec/plan 머리말의 댕글링 참조를 잡지 못한다(템플릿 플레이스홀더 제외 규칙을
새로 만들지 않기 위한 선택).

**출처**: BACKLOG-003, `docs/superpowers/specs/2026-08-05-backlog-status-sync-design.md`.
