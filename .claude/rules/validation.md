# 검증 (Validation & Testing)

## 기본 원칙

- 코드를 작성하면 반드시 검증 단계를 거친다.
- "작동할 것 같다"는 추측으로 완료 처리하지 않는다.
- **테스트가 없는 기능 추가는 완료로 간주하지 않는다.**(→ `requirements.md` 상태 ⚠️ 상한)

## 검증 단계 순서

1. **빌드** — 변경 후 가장 먼저. 빌드 에러가 있으면 다음 단계로 넘어가지 않는다.
2. **단위 테스트** — 변경한 함수/모듈. 새 기능엔 테스트도 함께 작성.
   - happy path / 경계값·엣지 / 에러·예외 / 외부 의존성 mock.
3. **통합 테스트** — 여러 모듈이 함께 동작하는 흐름(API·DB·외부 연동).
   - 주요 사용자 시나리오 / 서비스 간 데이터 흐름 / 실패·롤백.
4. **타입 검사 & 린트** — type-check, lint(자동 수정 가능 항목은 lint:fix).
5. **수동 검증** — UI는 브라우저 직접 확인, 환경 의존 동작은 스테이징, 성능은 응답시간 비교.

> 실제 명령어는 프로젝트별 README/`commands.md`에 기록한다(예: `npm run build`, `npm test`).

## 완료 체크리스트 (PR/커밋 전)

```
- [ ] 빌드 성공
- [ ] 기존 단위 테스트 통과
- [ ] 새 기능에 대한 단위 테스트 추가
- [ ] 통합 테스트 통과 (해당 시)
- [ ] 타입 에러 없음
- [ ] 린트 경고 없음
- [ ] 수동 동작 확인
- [ ] 구현 현황 표·todo·changelog 갱신
```

## 테스트 실패 시 대응

1. 에러 메시지를 먼저 읽는다(추측 금지).
2. 실패 케이스만 격리해 재현한다.
3. 원인을 파악한 뒤 수정한다.
4. 수정 후 전체 스위트를 다시 실행한다.
5. 정당한 이유 없이 테스트를 삭제·skip 하지 않는다.

> 디버깅은 superpowers `systematic-debugging`, 구현은 `test-driven-development` 스킬을 따른다.
