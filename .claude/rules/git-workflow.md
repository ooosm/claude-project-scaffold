# Git 워크플로 (Branching & PR)

> 브랜치 전략을 **위험도 기반 하이브리드**로 규정한다. "항상 브랜치" / "항상 메인"의
> 단일 규칙보다, 변경의 위험도에 따라 분기하는 편이 특히 1인 개발에 효율적이다.
> harness 철학과 연결: **로컬은 부드럽게, 병합 지점은 엄격하게**(→ `commands.md`, DEC-006).

## 핵심 규칙 — 위험도로 분기

> **작고 안전한 변경은 메인에 직접, 위험/장기/배포/게이트/병렬 작업은 브랜치+PR.**

### 메인에 직접 커밋해도 되는 경우

- 문서·설정·방법론 변경 등 **런타임이 없는** 변경.
- 한 커밋으로 끝나는 **자명한 수정**(오타·사소한 리팩토링).
- **배포 파이프라인이 없는** 개인 도구·프로토타입·스파이크(깨지면 즉시 fix-forward).

### 브랜치 + PR을 써야 하는 경우

- 메인 → 프로덕션 **자동 배포**가 걸려 메인이 항상 배포 가능해야 할 때.
- **여러 커밋에 걸치는 기능**이나 **위험한 리팩토링**(중간 상태가 메인에서 깨지면 안 됨).
- **CI로 정말 막고(gate) 싶을 때** — 브랜치 보호 + 필수 PR이 있어야 strict 검사가 머지를 차단한다.
- **Claude 에이전트/worktree를 병렬로** 돌릴 때(격리 없으면 서로 파일을 덮어씀).
- **버릴 수도 있는 실험**(브랜치째 삭제하면 메인 무결).

## 브랜치 네이밍

`<type>/<kebab-slug>` — type은 커밋 타입과 동일(`feat`·`fix`·`refactor`·`docs`·`chore`).
예: `feat/user-auth`, `fix/token-refresh`, `refactor/payment-module`.

## PR = 게이트 (특히 1인 개발)

- 혼자면 자기 PR을 자기가 승인하므로 **동료 리뷰 효과는 약하다**. 솔로 PR의 실질 가치는:
  1. **CI 차단 게이트** — 메인 단독에서는 CI가 사후 통보일 뿐 나쁜 커밋의 메인 진입을 못 막는다.
     PR + 브랜치 보호가 있어야 `check-docs --strict`(→ `.github/workflows/`)가 머지를 실제로 차단한다.
  2. **diff 전체를 리뷰어 시점으로 한 번 멈춰 보는 강제 포즈** — `/code-review`·`security-review` 연계.
- 규율을 강제하고 싶으면 **메인에 브랜치 보호를 걸고 PR을 필수화**한다. 그 순간 strict CI가
  자문(advisory)에서 진짜 게이트(gate)로 승격된다.

## Claude Code 연계

- 하네스 기본값: **비자명한 작업이면 먼저 브랜치를 판다**(메인 직접 커밋은 안전 변경에 한정).
- 커밋·푸시는 **사용자가 요청할 때** 수행한다. 완료 시에는 **자동 갱신 묶음**을 함께
  포함해 커밋한다(목록 정본: `readme-sync.md`).
- 여러 작업을 병렬로 진행할 때는 git worktree로 격리한다(superpowers `using-git-worktrees`).

## 커밋 단위

- 한 커밋 = 논리적으로 완결된 한 단위(코드 + 테스트 + 관련 문서 갱신).
- 브랜치+PR은 squash-merge로 **기능당 1커밋**을 권장(메인 히스토리가 기능 로그로 읽힘).
- 커밋 메시지 형식은 `conventions.md`를 따른다.
