# 요구사항 관리 (Requirements)

> 방법론 구성요소 ⑤ 요구사항 2분할 + ④ 구현 현황 자동 갱신

## 두 문서로 분할

| 문서 | 관점 | ID | 내용 |
|------|------|----|------|
| `.claude/docs/01-impl-requirements.md` | **구현 관점** | `REQ-N-M` | 무엇을, 어떤 규칙/엔드포인트/데이터구조로. 기술적·검증 가능 |
| `.claude/docs/01-user-requirements.md` | **사용자 관점** | `FR-NN` | 사용자가 무엇을 할 수 있는가. `[ ]/[x]` 체크박스 |

- 두 문서를 ID로 **교차 링크**한다 (예: `FR-09 ↔ REQ-1-10`).
- 각 문서에 우선순위/미완성 표를 유지한다.

## ID 불변 규칙

- **REQ/FR ID는 한 번 발번하면 불변**이다. REQ의 Phase 간 이동은 금지 —
  이동이 필요하면 구 ID를 `(Deprecated → REQ-N-M)` 로 표기해 남기고 새 ID를 발번한 뒤,
  참조(FR·DEC·spec/plan)를 갱신한다. ID가 바뀌면 과거 문서의 참조가 전부 깨지기 때문이다.
- 번호는 마지막 번호 +1. 병렬 세션/worktree 작업 후에는 `scripts/check-docs.sh`로
  번호 중복·댕글링 참조를 확인한다.

## REQ 작성 형식 (구현 관점)

```markdown
### REQ-1-10: [요구사항 제목]
- **설명**: 시스템이 무엇을 해야 하는가(기술적·검증 가능하게).
- **규칙/엔드포인트/데이터구조**: ...
- **검증 방법**: 어떤 테스트로 충족을 확인하는가.
  테스트 파일/케이스를 명시한다(예: `foo.spec.ts` "expired token → redirect").
  자동 테스트가 성립하지 않으면 수동 검증 절차를 명시(→ `validation.md` 예외 규칙).
- **관련**: FR-09, DEC-012
```

> **검증 방법에 테스트 참조를 명시**하면 FR → REQ → 테스트로 이어지는
> 요구사항-시험 추적표를 납품 시 그대로 뽑을 수 있다.

## FR 작성 형식 (사용자 관점)

```markdown
- [ ] **FR-09**: 사용자는 [무엇]을 할 수 있다. (관련: REQ-1-10) — 우선순위: P1
```

> **큰 기능은 동작 흐름 문서와 상호 링크**한다 — 여러 컴포넌트/트리거에 걸치는 FR/REQ는
> `docs/how-it-works.md`의 해당 섹션을 링크해 납품용 추적성을 강화한다(→ `readme-sync.md`).

## 구현 현황 요약 표 (`01-impl-requirements.md` 상단에 유지)

상태 기호: ❌ 미착수 / ⚠️ 진행중·부분 / ✅ 완료(테스트 포함).

```markdown
## 구현 현황 요약
_최종 업데이트: YYYY-MM-DD_

| REQ | 제목 | 상태 |
|-----|------|------|
| REQ-1-1 | ... | ✅ |
| REQ-1-2 | ... | ⚠️ |

### Phase별 카운트
| Phase | ✅ | ⚠️ | ❌ | 합계 |
|-------|----|----|----|------|
| Phase 1 | 3 | 1 | 0 | 4 |
```

## 자동 갱신 규칙 (필수)

- **각 단계/태스크 완료 시 구현 현황 요약 표를 즉시 갱신**한다(사용자 요청 없어도).
- **"테스트 없는 기능 추가는 완료(✅)로 간주하지 않는다."** 테스트가 없으면 최대 ⚠️.
  예외: 자동 테스트가 성립하지 않는 작업은 `validation.md`의 예외 규칙에 따라
  수동 검증 완료를 근거로 ✅ 가능(검증 방법에 절차 명시 필수).
- 상태 변경 시 함께 갱신할 문서 목록은 **`readme-sync.md`의 "완료 시 자동 갱신 묶음"이
  단일 정본**이다 — 여기서는 재정의하지 않는다.
